| D-023 | Media Library is the single business-asset workspace for LITUBO, serving Product Center, AI Source, future Content Center and Settings/Branding through one stable Media UUID/ID; physical path is never the reference identity. Folders are governed in two distinct classes. **Protected System Folders** provide stable business classification and can never be renamed, moved, trashed or archived by a customer; whether a customer may create children beneath one is stated explicitly per folder, never inferred. **Customer-managed Folders** are the dynamic descendants of an explicitly declared customer-manageable zone, and may be created, renamed, moved, trashed and restored inside that zone only. A path that is neither protected/frozen nor inside a declared customer-manageable zone remains `unknown` and stays FAIL-CLOSED: unknown is never treated as customer-managed, and no path acquires write or management rights by absence from a list. The existing `ambiguous`, `legacy-read-only` and `conflict-frozen` protections continue unchanged and are evaluated before any customer-management rule. Folder-management policy (may this folder be created/renamed/moved/trashed) is a separate dimension from file-content policy (may files be uploaded here, may this be a move target); one state must not answer both. Renaming or moving a file or folder must never change a business asset UUID or break a Product, Content, Branding or AI Source reference, and must never create a second physical copy. In V1, Delete means reversible Trash/Archive; permanent deletion is not available and would require global reference protection first. Folder names and paths are organisation aids only — never the authoritative source of product model, specification, language, file role, AI truth or published truth. The "Reusable Core, LITUBO First" principle of D-022 continues to apply. | Confirmed |
| D-024 | **Unified AI Source Extraction Contract.** Every AI source format is described once, in the shared format contract (`utils/aiSourceFormats.ts`) that the server and the browser both read, which records separately whether the Media Library stores a format and whether AI Source Intake can analyze it. (1) Every format — TXT, CSV and TSV today; PDF, DOCX, XLSX and images later — is reduced to the same bounded `ExtractedSource` (`displayName`, `fileType`, `text`) before anything reaches a model; no structured metadata, page locator, path, Media UUID or file name is added to the provider input. (2) All formats use the one existing Proposal Engine: one analysis, one provider call, one merged proposal; there is no per-format AI path. (3) Only TXT, CSV and TSV are AI-readable now. (4) PDF, DOCX, XLSX and images become AI-readable only after their own implementation module has passed acceptance; legacy DOC and XLS are not part of V1. (5) A source that is not read is reported with a fixed failure code, and each code maps to one fixed, safe message in the shared contract; no stack trace, path, stderr, container detail, UUID, token or source fragment is ever returned. (6) The reading stage of one analysis has a V1 budget of 60 seconds (`MAX_TOTAL_EXTRACTION_MS`), so reading plus the provider call stays inside the 120-second Generate single-flight window; a source the budget does not reach is reported as not analyzed, sources already read are still analyzed, and when none is readable no provider is called. (7) Original binary files are never sent to the text provider — only bounded extracted text. (8) Product-model relevance (product code and multi-model attribution in the prompt) is a separate, later module and is not part of this contract. D-022 continues to apply: this decision introduces no plugin system, registry framework, new service or new dependency. | Confirmed |
| D-025 | **Product Model Attribution Guard.** Every AI prompt identifies the current product, and a value reaches a proposal only when its source attributes it to that product. (1) Every AI prompt names the current product by its `name_en`. (2) When the product has a non-empty `product_code`, the current-product context also carries that code exactly as stored; when it has none, no code line is written — never "null", "unknown" or a placeholder. Both values pass the same prompt sanitization as every other non-source field. (3) `product_code` is never created, filled in or changed by AI or anywhere on the AI path; Analyze only reads it. (4) A source may describe several product models. A value may be extracted only when the source clearly attributes it to the current product — by its product code, by clearly naming the current product, or by being clearly and exclusively about it — and a value stated for all models in a series may be used only when the source itself says so. (5) When product attribution is ambiguous, the value is omitted. (6) A value that belongs to another product model is never copied, including as a conflict candidate. (7) V1 performs no fuzzy model matching: no edit distance, prefix, similar-model, filename or folder-name inference, and a merely similar model name or code is not the current product. (8) `model_or_series` is not used as the product's identity, because it can name a series, platform or product family rather than one model. (9) The guard is part of the shared prompt contract (`server/utils/aiTargetContract.ts`) that every AI Target includes, not an instruction local to one Target, and it applies within the one provider call of one analysis — never as an additional call. Text marked `[?]` could not be read reliably, and no value may be inferred from it. (10) A semantic change to the shared prompt contract raises `PROMPT_CONTRACT_VERSION`; that version and the product code are both part of the analysis fingerprint, so an analysis made under an earlier contract or a different product identity is never replayed. D-022 and D-024 continue to apply: no new service, dependency or AI-readable format is introduced, and `ExtractedSource` is unchanged. | Confirmed |
| D-026 | **Isolated PDF Extraction.** Text-layer PDFs are an AI source, read by an isolated extractor and never inside the Nuxt process. (1) A text-layer PDF is an AI-readable source in AI Document Source V1 (`aiReadableNow = true` in the shared format contract). (2) The original PDF is never sent to an AI provider or to any external PDF, OCR or file service; only bounded extracted text reaches the one provider the administrator selected. (3) PDFs are read by `document-extractor`, a security-isolation sidecar container whose only job is untrusted PDF bytes in, bounded text or one fixed failure code out. (4) The sidecar has no database, Directus, AI-provider or product access; it receives no project secret and no environment file, mounts no volume and keeps nothing: the PDF is written only to its tmpfs `/tmp` under a name the service generates, and deleted when the task ends. It sits on an internal Docker network with no route out. Docker publishes no port for a container that is only on an internal network, so a gateway container built from the same image publishes `127.0.0.1:8787` and forwards each connection, unread, to the one fixed address `document-extractor:8787`; the gateway parses nothing. (5) The parser is Poppler — `pdfinfo` for the page count and encryption, `pdftotext -layout` for the text — run as child processes with an argument array, never through a shell, with no retry and no fallback parser. (6) Isolation has two hard layers: every Poppler process runs under an OS address-space limit (`prlimit --as`, 384 MB, no core dump), and the container is capped at 512 MB of memory with no extra swap, 1 CPU and 64 processes, with a read-only root filesystem, every Linux capability dropped, no-new-privileges and a non-root user. (7) V1 limits: 20 MB per PDF (checked in Nuxt against trusted file metadata and again while streaming the download, and checked again by the sidecar itself), 50 pages, 20,000 characters of text, and one 15-second deadline for the whole task — queue wait, `pdfinfo` and `pdftotext` together — enforced by killing the process. One PDF is parsed at a time, at most three wait, and a further request is told `busy`. (8) A PDF over 50 pages is refused (`too_many_pages`), never silently cut to its first pages, because a later page may hold a value that contradicts an earlier one. (9) A scanned PDF with no text layer returns `no_text`: V1 performs no OCR and no vision. A password-protected PDF, and in V1 any encrypted PDF, returns `encrypted`. (10) A PDF's text returns to the unified `ExtractedSource` and the one existing Proposal Engine: the same content dedupe, fingerprint, character caps, reading budget (`MAX_TOTAL_EXTRACTION_MS`), product model relevance guard (D-025) and single provider call as every other source. There is no PDF-specific AI engine, prompt, provider or table. (11) D-022 continues to apply: this is a narrow exception for one security-isolation sidecar and its port gateway only, and authorises no general microservice architecture, AI platform, business service or file-conversion platform. (12) Production deployment, and a production runtime capacity check of RAM and CPU, remain separately authorised steps; this decision deploys nothing. | Confirmed |
| D-027 | **Bounded XLSX Extraction.** Standard .xlsx workbooks are an AI source, read inside the Nuxt process by a bounded streaming reader and never loaded whole. (1) A standard `.xlsx` workbook is an AI-readable source in AI Document Source V1. (2) `.xlsx` is accepted by the Media Library upload route and is AI-readable (`mediaUploadSupported = true`, `aiReadableNow = true` in the shared format contract); an upload must match both the official MIME type and the extension. (3) Legacy `.xls` and macro-enabled `.xlsm` are not part of V1: the Media Library refuses them, and a legacy `.xls` upload is told to save the file as `.xlsx`. A macro-enabled, template, add-in or binary workbook disguised as `.xlsx`, and a package carrying a VBA project or an Excel 4.0 macro sheet, is refused as `unsupported`; no macro is ever read or run. (4) The reader is a bounded in-process OOXML streaming parser; no service, container or sidecar is added. (5) The ZIP container is read with `yauzl` and XML is parsed with `saxes`, both pinned to exact versions (`yauzl` 3.4.0, `saxes` 6.0.0, plus `@types/yauzl` 3.4.0 as a development dependency only); production code contains no hand-written ZIP parser. (6) No workbook is loaded whole: no SheetJS (`xlsx`), no ExcelJS, no DOM or whole-document XML parsing, and every limit is enforced while parsing rather than on a finished result. (7) Decompression limits count the bytes actually inflated, never the sizes an archive declares: at most 16 MB of shared-strings XML, 16 MB of styles XML, 32 MB per worksheet XML, 4 MB for any other part read, and 64 MB across all parts read. An archive may hold at most 1,000 entries. An unsafe entry name (absolute, drive-letter, `..`, backslash, NUL, or one that becomes any of these under NFKC) and a part name that appears twice are refused as `malformed`, so no parser differential can choose between copies. A DOCTYPE, DTD or entity declaration in any part is refused as `malformed`, so no entity is ever expanded; XML depth is capped at 128 and any single XML token at 1 MB. Only the parts the workbook needs are opened — never external links, embedded objects, drawings, charts, media, custom XML or macros. (8) Only visible sheets are read. Hidden and very hidden sheets, hidden rows and hidden columns — including zero-height rows, zero-width columns and values hidden by a `;;;` number format — never reach AI. (9) A formula contributes only the value Excel last saved for it. Formulas are never recalculated; formula text, external workbook paths and external links are never output; a formula with no cached value, or with an error value, is empty. (10) The extracted text keeps the workbook's structure: `Sheet:` for each visible sheet, `Columns:` for its first non-empty visible row (an empty header cell is named by its column letter), and one line per data row with cells separated by ` | ` (a `|` inside a value is escaped). A merged cell's value is looked up from the merge's anchor, never inherited from the row above; empty rows and fully empty columns are left out. Numbers are written without floating-point noise, and only explicit percentages, a number followed by one simple quoted unit, and unambiguous date and time formats (1900 and 1904 date systems) are interpreted; any other value is written as stored and no Excel formatting engine is reproduced. (11) When the current product has a non-empty `product_code` containing at least one letter and one digit, a sheet may be narrowed deterministically. Normalization is NFKC, trim, upper case, and removal of whitespace, `-`, `_` and `.`. A cell may name several models separated by `/`, `,`, `;`, `|`, `、`, `，` or a line break, and each fragment is compared on its own. A column-oriented sheet keeps its label column and every column whose header names the exact code; a row-oriented sheet keeps its header and the data rows with a cell naming the exact code; the text then states `Filtered to exact product code: <code>`. A sheet that does not name the code is kept whole — a single-model workbook often has no model column. (12) Model matching is exact only: no edit distance, prefix, suffix, substring, similar-model, filename, folder-name or AI-call matching. `LT180` is not `LT180C`, and `LT180C-S` is not `LT180C`. (13) Narrowing only reduces the context and is not a fact check: the D-025 Product Model Attribution Guard still applies in full, inside the same single provider call, followed by human review. (14) A product without a `product_code` — or with a code lacking a letter or a digit, which could equal an ordinary cell value — is not narrowed; the whole bounded workbook goes to the guard, and no product code is required before a workbook can be analyzed. (15) V1 hard limits: 10 MB per file (checked against trusted file metadata, again while streaming the download, and again by the reader); 50 sheets in a workbook and 10 visible sheets; 5,000 rows per sheet and 20,000 rows in total, counting rows that actually hold a value, hidden rows included; 100 used columns; 200,000 non-empty cells scanned and 20,000 cells output; 100,000 shared strings and 4,000,000 shared-string characters; 500 characters per output cell; 1,000 merged ranges and 10,000 cells per merge; 20,000 characters of text, and no more than the workbook's share of the combined 60,000-character cap when several sources are selected; an 8-second processing deadline, or less when the analysis reading budget (`MAX_TOTAL_EXTRACTION_MS`) has less left. One Office document is parsed at a time with at most three waiting, a further request is told `busy`, and time spent waiting is taken from the same deadline. A workbook over any limit is refused as a whole with one fixed code (`too_large`, `too_many_sheets`, `too_many_rows`, `too_many_cells`, `too_complex`, `timeout`, `busy`): a visible sheet or row is never silently dropped and the text is never cut. `no_relevant_rows` means only that no visible sheet has a data row; it never means the product code was not found. The deadline is enforced by the application: the reader runs in-process with no OS-level memory limit, and its safety rests on bounded input, counted inflation, streaming XML, these counters and the single-parse gate. (16) No database schema, Directus schema or collection is added; workbooks stay in the Media Library and are linked to products through `products_files`. (17) A workbook's text becomes one `ExtractedSource` (file type `Spreadsheet`) in the one existing Proposal Engine — the same content dedupe, fingerprint, character caps, reading budget, relevance guard and single provider call as every other source — and the original workbook is never sent to a provider. (18) Extracted workbook text exists only for the lifetime of one analysis and is never persisted, cached or logged. D-022 and D-024 continue to apply: this decision introduces no Office plugin framework, document-parser registry, conversion platform or AI engine of its own. | Confirmed |
| D-028 | **XLSX Semantic Fidelity Correction.** A workbook's text shows each number as Excel shows it, and exact product-code narrowing of a column-oriented sheet keeps the columns that describe each row. This corrects D-027 (10) and (11) on these two points only; the rest of D-027 stands. (1) A number stored under a V1-supported simple number format is written with the decimals that format shows, never with the hidden precision it is stored with. The supported formats are a plain number — `0`, `0.0`, `0.00`, `0.000`, the same with a thousands separator (`#,##0`, `#,##0.0`, `#,##0.00`), and the built-in formats 1–4 and 37–40 — a percentage (`0%`, `0.0%`, `0.00%`, built-in 9 and 10), and a plain number followed by one simple quoted unit (`0" mm"`, `0.0" kW"`, `0.00" kg"`, `#,##0.0" bar"`). A `0` decimal place is always written and a `#` decimal place only when its digit is not a trailing zero; at most 30 decimal places are read, and a longer run is written as the stored number. So 0.45 under `0.0` is `0.5`, 0.45 under `0.00` is `0.45`, 0.456 under `0.00" kW"` is `0.46 kW`, 180 under `0" mm"` is `180 mm`, -0.45 under `0.0` is `-0.5`, and 0.456 under `0.00%` is `45.60%`. (2) Rounding is ordinary decimal rounding, half away from zero, applied to the 15 significant digits Excel keeps and never to the binary value, so 0.35 under `0.0` is `0.4` and 1.005 under `0.00` is `1.01`, as Excel shows them. It only follows the precision the format displays: it never adds precision and never recalculates a value. No thousands separator is written and the decimal mark is always `.`, because both marks come from the reader's locale rather than from the workbook; the sign of a negative number is always written. (3) A formula still contributes only the value Excel last saved for it and is never recalculated; a cached number follows the same supported formatting. (4) Dates and times (1900 and 1904 date systems), a value hidden by a `;;;` format, and the stored-number fallback for every other format — currency, scientific, fractions, conditions, several meaningful sections, elapsed time, padding and locale-specific codes — are unchanged; no Excel formatting engine is reproduced. (5) When a sheet is narrowed as column-oriented (D-027 (11)), every visible column to the left of the first column whose header names the exact product code is kept as descriptor context — the parameter, unit or range that describes each row — together with every column whose header names the exact code, for the data rows with a value under that code. Descriptor columns are chosen by position, never by interpreting what a header says, and a column with no value in the header or in the kept rows is left out. (6) To the right of the first matched column, only a column whose header names the exact code is kept: another model's column, and a column between model columns such as a note, are left out. Because the rule reads position rather than meaning, a column to the left of the first match is kept whatever its header says, including another model's column, which keeps its own header; attribution stays with the D-025 guard. (7) Hidden columns, including zero-width columns, remain excluded wherever they are. (8) The row-oriented rule, exact-only matching (no fuzzy, edit-distance, prefix, suffix, substring, filename, folder-name or AI-call matching), the rule that only a code with both a letter and a digit narrows a sheet, the `Filtered to exact product code:` line, keeping a sheet whole when it does not name the code, and the D-025 Product Model Attribution Guard are unchanged. (9) No source format, dependency, database or Directus schema, collection, provider adapter, provider behavior or provider call is added; `ExtractedSource`, the shared prompt contract and the one analysis path are unchanged. | Confirmed |
