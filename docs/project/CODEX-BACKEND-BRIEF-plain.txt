## 2. 任务 A：前后端是否对应

### 2.1 要做什么

**逐字段比对**：前端每个页面渲染的字段，后端是否真的提供、类型是否一致、是否可能为空。

### 2.2 输出格式（每个页面一行）

| 前端页面 | 渲染字段 | 后端接口 | 字段来源（Directus 列名） | 对应 | 问题 |
|---|---|---|---|---|---|

**示例**

| 页面 | 字段 | 接口 | 来源列 | 对应 | 问题 |
|---|---|---|---|---|---|
| `/products/checkweighers` | 系列名 | `/api/cms/products/checkweighers` | `checkweigher_series` | ✅ | — |
| `/resources/insights/[slug]` | 封面 fit | — | **无对应列** | ❌ | 前端用硬编码 slug 清单决定 contain/cover（A08 临时方案） |

### 2.3 重点查这些"不对应"

1. **前端有、后端没有**：前端硬编码的值，后端没有字段支撑
   - 例：A08 的 `CONTAIN_SLUGS` 写在前端，后端没有 fit 字段
   - 例：系列卡的图标、文案
2. **后端有、前端没显示**：字段存在但页面没渲染
   - 例：`ai_*` 七个字段
   - 例：`posts.topics` / `faq_group` 是否用上
3. **类型不一致**：Directus 是 `string`，前端当 `number` 用之类
4. **可空但前端没兜底**：字段为 null 时页面会不会崩
5. **文案在代码里、后台改不了**：**这是最大的一类**。四页 Company、Support、Resources 的正文大量写在 `.vue` 里

### 2.4 已知的最大不对应

**大量正文文案硬编码在前端代码里。**

| 页面 | 硬编码内容 |
|---|---|
| `/company/*`（4 页） | 几乎全部正文、卡片标题、说明 |
| `/support/*`（5 页） | 全部字段标签、帮助卡、FAQ |
| `/resources/downloads` `/videos` | 全部文案 |
| `/products/checkweighers` | 五个系列的名称与说明 |

**这些业主在后台改不了，只能找开发改代码。**

**请列出哪些该迁到后台、哪些保持代码里更合理**（不要建议"全部迁"——静态长文案迁进 CMS 反而难维护）。

### 2.5 修正方案

针对每一类不对应，给出：
- **改前端** 还是 **改后端** 还是 **加字段**
- 为什么这样改（成本 / 风险 / 可维护性）
- 是否需要数据库迁移？能否回退？

## 3. 任务 B：后台重新设计（在原基础上）

### 3.1 目标（业主原话）

> 「最好用颜色区分开来，让人容易看到。让其结构更加清晰。这样，人不容易累。」

**翻译成设计要求：**

1. **视觉分区**：不同功能区用颜色区分（不是花哨，是让眼睛能快速定位）
2. **信息密度降低**：一屏不要塞太多
3. **层级清晰**：一眼看出"我在哪、这页能做什么"
4. **减少疲劳**：长时间用不刺眼、不迷失

### 3.2 请先解决三个结构问题

| # | 问题 | 建议方向（你来判断） |
|---|---|---|
| 1 | 两套产品编辑 UI（`products/[id]` 与 `product-workspace/[id]`） | **合并成一套**，另一套保留跳转或删除 |
| 2 | 文章两个数据源（`posts` vs `content_items`） | **统一到 `posts`**（前台在用），或明确分工并标注 |
| 3 | 36 个页面无导航分区 | 建**统一的后台导航**，按颜色分区 |

### 3.3 颜色分区的建议（可调整）

| 区 | 颜色倾向 | 包含 |
|---|---|---|
| **内容** | 绿（品牌色系） | 产品、文章、页面内容、Hero 图 |
| **人** | 蓝 | 询盘、访客 |
| **素材** | 橙 | 媒体库、文件 |
| **设置** | 灰 | 站点设置、账号 |
| **AI** | 紫 | AI 提案审查、AI 源接入 |

**要求：颜色只做辅助识别，不能只靠颜色区分**（色盲用户）。每个区必须有图标或文字标签。

### 3.4 必须保留

```
✅ 现有的发布流程（draft → published）
✅ 现有的权限模型
✅ 现有的 AI 提案审查流程（ai-proposal-review / ai-source-intake）
✅ 现有的媒体引用保护、软归档
✅ 英文 URL 不变
```

### 3.5 允许的调整幅度（业主明确）

> 「必要的地方，结构做一个微调是可以，但是不能大动，以免产生问题。」

**允许：**
- 合并重复的页面
- 加导航、加分区色
- 调整区块顺序
- 加字段、加说明文字
- 改按钮位置

**不允许：**
- 重写数据库模型
- 换技术栈
- 换认证方式
- 删除现有功能
- 改前台 URL
- 大改 API 契约

**判断标准：任何一步做错，能不能 5 分钟内回退？不能就不做。**

## 4. 任务 C：把 Hero 图和内容交给后台管

### 4.1 业主需求

> 「后端可以管理前端的页面的 hero 图，内容。」

### 4.2 现在的问题

| 页面 | Hero 图 | Hero 文案 |
|---|---|---|
| 首页 | CMS（`site_content`） | CMS ✅ |
| 产品分类 | 部分 CMS | 部分 |
| `/company/*` 4 页 | **代码里写死** | **代码里写死** |
| `/support/*` 5 页 | **无图** | **代码里写死** |
| `/resources/*` 3 页 | **代码里写死** | **代码里写死** |

### 4.3 要做的

给这些页面加**可管理的 hero**：

1. 复用现有 `site_content` 模型（已有 9 条首页块），**不要新建万能 CMS**
2. 扩展方式：
   - 加 `page_key`（如 `company.about` / `support.spare-parts`）
   - 加 `hero_image`（媒体引用）
   - 加 `hero_title_*` / `hero_intro_*`（三语字段）
3. 前端读不到时**回退到当前代码里的默认文案**（不能因为后台没配就空白）
4. 后台提供**预览**：改了能立刻看到效果

### 4.4 约束

```
❌ 不要给每个页面新建一个 collection
❌ 不要让 hero 变成"必须后台配置才能显示"
❌ 不要迁移现有 4 页的全部正文（只迁 hero，其余按任务 A 的结论决定）
✅ 用现有 site_content，加最小字段
```
