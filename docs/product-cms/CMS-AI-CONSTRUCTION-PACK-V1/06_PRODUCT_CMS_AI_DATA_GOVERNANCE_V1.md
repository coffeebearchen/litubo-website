# LITUBO 产品 CMS 与 AI 数据治理决策 V1

**日期：** 2026-09-05  
**状态：** 已确认的 V1 治理基线；后续视觉设计、数据库/API 设计与 Claude Code 施工必须遵守。  
**范围：** LITUBO 官网后台的 Product Center、Media Library、Resources/Content 引用、产品导入、AI 产品资料工作台、审核与公开发布。  
**不包含：** 本文件不授权实施代码、数据库迁移、模型 API Key、费用、发布、部署或导入真实产品资料。

---

## 1. 一句话原则

> **原始资料是证据；人工确认后的结构化产品事实（Product Truth）才是唯一可信来源；网站、Datasheet、PPT、报价、邮件和视频都只能从对应版本的可信事实生成。**

AI 可以协助提取、填写、检查和生成建议；AI 不能替代技术确认、公开授权或发布决定。

---

## 2. 已冻结的系统边界

| 领域 | 唯一职责 | 不负责 |
|---|---|---|
| **Media Library** | 业务媒体唯一来源；文件 UUID、存储、引用计数、生命周期与媒体元数据。 | 产品分类、产品文案、网站页面结构。 |
| **Product Center** | 产品型号、规格、关系、Draft/Review/Published 流程、产品详情页固定模块。 | 物理存储第二份图片/PDF，或保存客户项目配置。 |
| **Content Center** | Applications、Case Studies、Insights、网站内容页等内容记录。 | 把内容类型当作媒体文件夹或产品分类。 |
| **Resources** | 手册、Datasheet、证书、图纸等“可对外使用的资源记录”；每条资源引用已批准 Media UUID。 | 自动把原始资料或私有文件公开。 |
| **Technical Matching / Project** | 客户需求、包装/产线/速度/测试要求、选配、报价、FAT 与交付资料。 | 覆盖通用产品型号事实或自动进入公开产品页。 |

**固定规则：** 所有业务内容只能引用 Media UUID，不复制第二套文件或写死文件路径。`is_public` 不是唯一安全开关；公开展示、下载权限和资料来源保密级别必须分开处理。

## 3. 产品、系列与客户项目的关系

```text
Product Family（可选系列分组）
        └─ Product（一个可对外识别的具体型号 / product_code）
                ├─ Product Revision（Draft / Review / Published 的内容版本）
                ├─ 规格、媒体引用、资源、固定页面模块
                └─ 可被多个 Technical Matching / Project 引用

Technical Matching / Project
        ├─ 客户应用、产线、包装、速度、灵敏度、选配、报价、FAT
        └─ 只能关联产品候选；不等于产品通用事实
```

### D-01：产品最小单位

- 一个 `Product` = 一个可对外识别并可能拥有独立详情页的具体型号。
- `product_code` 是稳定、全局唯一、不可复用的业务编码；对外使用后不得静默改写。
- `Product Family` 仅用于分组、导航或系列聚合；一期不实施复杂 Variant 配置器。
- 新型号、对外参数不同的变体必须有新的 `product_code`；不以产品名称、图片文件名或 AI 相似度判断身份。

### D-02：标准型号与客户定制分离

- 公开产品页描述的是**标准型号或可公开确认的系列能力**。
- 客户特定的输送线、检测精度、包装、速度、剔除方式、报价、交期、测试条件、FAT/验收结果，属于 `Project / Technical Matching`，默认私有。
- Project 可关联一个或多个产品候选；但不得反向自动修改 Product Truth。

## 4. 产品数据结构与详情页

### D-03：字段模板优先于自由填写

- 每个产品类别必须有可版本化的字段模板（Schema）。
- Schema 至少定义：字段 key、数据类型、单位、枚举、是否可多值、必填规则、公开规则、是否必须有来源证据、对应详情页模块。
- 产品数据至少分为：通用身份、分类/应用、规格项、媒体引用、资源引用、FAQ、SEO、页面模块、审核状态与来源证据。
- 不把全部参数塞入自由 JSON、富文本或单一大表；规格、媒体、资源、关系、页面模块均应结构化关联。

### D-04：详情页只能组装固定槽位

一期详情页固定槽位为：

```text
Hero → Overview → Capability Modules → Specifications
→ Gallery & Resources → Applications → FAQ → CTA → SEO
```

AI 只能向既定字段和模块提出建议；不能生成任意 HTML、改变全站视觉系统或自动创建新的页面结构。

## 5. 资料、媒体与证据治理

### D-05：媒体唯一来源与引用保护

- 每个业务文件在 Media Library 中只存一份，以 Media UUID 被 Products、Resources、Content、Branding 等引用。
- 所有关联必须记录角色，例如 Hero、Gallery、PDF、Certificate、Drawing、Source Evidence。
- 已发布 Revision 必须固定引用明确的媒体版本；不得以替换同一 UUID 的文件方式，静默改变历史已发布页面或已生成资料。
- 一期不得物理删除业务媒体；删除/归档必须先进行全局引用检查，并支持可恢复。
- 旧目录不自动迁移；迁移必须以明确计划和引用核对为前提。

### D-06：可见性与公开下载必须分开

每个资料至少具备以下业务判断：

| 层级 | 含义 | 默认 |
|---|---|---|
| 私有来源证据 | 原始 PDF/Excel/PPT、图纸、报价、客户资料、未审核文件。 | 私有，不进入公开 API、前台或 Git。 |
| 内部可复用 | 允许后台团队使用，但未授权公开。 | 仍不可下载或对外展示。 |
| 已批准公开使用 | 已确认可作为产品图片、公开资源或页面内容。 | 仍须按具体角色与下载策略展示。 |

“关联到产品”不等于“允许公开下载”。产品发布也不能自动公开原始 PDF、证书、图纸或私有图片。

资料的“允许 AI 处理”也必须独立于“允许公开”：客户资料、私有报价或内部图纸即使可被后台人员查看，也只有经明确授权后才可进入某个 AI source snapshot。

### D-07：来源证据与冲突规则

- 所有技术参数、认证、性能和客户案例结论都必须保留来源：文件 UUID/版本、PDF 页码、Excel Sheet 与单元格范围、图片或图纸区域等。
- 如确需人工确认无原始文件的历史事实，必须记录具名审核人、确认理由与适用范围；该例外不能被 AI 当作一般来源规则。
- 无来源、资料模糊、型号归属不明或多来源冲突时，必须进入 `Needs confirmation`，AI 不得猜测或自行选择。
- 默认字段优先级：
  - 尺寸、机械接口、结构：技术图纸优先；
  - 性能与操作范围：已批准 Datasheet/说明书优先；
  - 认证事实：证书原件优先；
  - 价格、交期、客户适配：仅项目/报价或人工确认，不能作为通用产品事实。
- 旧网页文案、营销图片、历史报价不能单独成为技术事实依据。

### D-08：系列共享资料必须显式授权

- AI 默认只读当前型号 Draft 明确关联的资料。
- 仅人工明确标记为“本系列可共享”的资料，才可在指定 Product Family 内被其他型号读取。
- 共享资料只能提供通用能力或模板依据；型号专属参数、图片、证书仍必须逐型号确认。

## 6. 版本、审核与发布

### D-09：状态机固定，完整度不是状态

产品内容生命周期固定为：

```text
draft → review → published → archived
```

- 完整度、缺资料、冲突、AI 是否运行完成均为计算结果或问题状态，不得替代上述生命周期。
- 只有 `published` revision 可进入公开产品 API、前台详情页、sitemap 与搜索引擎。
- Draft、staging、AI 建议、私有来源资料绝不可公开。

### D-10：已发布内容通过新 Revision 修改

- 已发布产品的实质修改必须生成新的 Revision Draft；线上继续保留旧 Published revision，直到新版本审核通过。
- 通过审核后才原子替换前台读取的 Published revision；应保留可回滚历史。
- 当 Product Truth 或来源资料变化时，依赖它生成的 FAQ、SEO、PPT、Datasheet、页面模块等必须标记“需要刷新”，不得静默更改对外内容。
- 产品进入 `archived` 后必须排除公开 API、产品列表与 sitemap；无替代型号时原 URL 返回 410，有明确替代型号时才允许做经过审核的跳转。

## 7. 多型号导入与单型号 AI 工作

### D-11：工作簿导入只建立 Draft，不批量生成网页

- 一期使用固定、版本化的多 Sheet 工作簿模板；`product_code` 是唯一身份键。
- 工作簿先进入 Import Batch / staging，完成字段映射、单位校验、重复检查、异常报告与人工预览后，才可创建 Draft。
- 缺少/重复 `product_code`、未知媒体、无效单位、未知枚举、必填字段缺失等阻断错误不得写入。
- 同 `product_code` 已存在时默认阻断并要求人工选择；不得静默覆盖已审核或 Published 内容。
- 执行导入最多创建或更新 Draft Revision；不得发布、不得批量生成详情页、不得批量接受 AI 建议。

### D-12：AI 的真正工作单位是单型号 Product Dossier

```text
一个 product_code
+ 一个 product_draft_id
+ 一个冻结的 source_snapshot_id
+ 一个 schema_version
+ 一次可审计的 AI task
```

- 单型号 AI 可：提取结构化字段、检查缺失/冲突、建议单位标准化、建议图片角色与 ALT、建议 FAQ/SEO/文案/固定页面模块，并为每项写证据与置信提示。
- 多型号导入后可排队处理多个 Draft；后台可异步排队，但每个 AI job 仍完全隔离，绝不能把多型号资料合并为一个提示上下文。
- 多型号页面的作用是“导入批次 + 逐个 AI 审核队列”；真正填表和修改发生在单型号 Product Dossier 中。

### D-13：AI 输出只能是 Candidate / Suggestion

- AI 只能创建版本化建议、证据、冲突与完整度结果，不得直接写入已确认字段、Published 内容或正式媒体。
- 人工对每项建议必须可选择：接受、编辑后接受、退回/拒绝；接受或人工编辑后字段默认锁定。
- 重新生成只产生新建议版本；如需让 AI 再建议已锁定字段，必须由有权限的人显式解除锁定并保留审计记录。
- AI 不可自动发布、撤回、删除、移动、归档正式媒体，也不可自动向外发送报价、邮件或技术承诺。

### D-14：AI 可共享的知识与不可共享的事实

| AI 可使用的全局知识 | AI 不可自动带入的资料 |
|---|---|
| 产品 Schema、字段词典、单位规则、品牌术语、页面模板、明确授权的系列通用资料。 | 其他型号参数、未关联图片/证书、客户询盘、客户附件、私有报价、全媒体库内容。 |

客户资料默认不参与模型训练。人工接受/编辑/拒绝记录可先沉淀为内部术语、规则与评测样本；只有未来获得明确授权、脱敏与可追溯控制后，才可讨论训练或微调。

## 8. 语言、资源与对外资料生成

### D-15：语言规则

- EN 是一期唯一必须审核并公开的产品语言。
- ES/PT 以独立翻译 Draft 保存，不因复制英文文本而自动成为已确认技术资料，也不得在未审核时进入公开路由、sitemap 或搜索引擎。
- 产品身份和数值事实不按语言重复；可翻译文本按照 `revision + locale` 管理。
- 后台中文仅是操作语言，不等于产品对外内容语言。

### D-16：所有生成资料读取 Product Truth

- 网站详情页、Datasheet、PPT、报价函、邮件、FAQ、内容文章、视频脚本与短视频，都应使用经授权版本的 Product Truth + 已批准媒体 + 固定模板生成 Draft。
- 未确认的原始资料、AI Candidate、私有客户资料不得直接进入对外生成器。
- 价格、交期、认证承诺、客户案例、测试结论属于高风险输出，必须人工审核后才可发送或公开。

## 9. 人员、权限与 API 边界

### D-17：最小角色模型

初期可由同一人兼任，但权限能力与审计责任必须分开：

| 角色能力 | 可做 | 不可做 |
|---|---|---|
| System Admin | 系统配置、角色配置、治理设置。 | 规避审计记录。 |
| Product Editor | 新建 Draft、关联资料、处理 AI 建议。 | 发布、绕过技术审核。 |
| Technical Reviewer | 确认参数、证据、资源可见性、提交/退回 Review。 | 自动公开私有来源。 |
| Publisher | 将已审核 revision 发布、撤回或归档。 | 修改技术证据而不留 Revision。 |
| Sales / Inquiry User | 查看授权产品、创建技术匹配或询盘。 | 把客户附件直接写入产品事实或 AI 训练集。 |

### D-18：服务层必须强制边界

- Directus 负责内部 CMS 数据与 Media Library；Nuxt/Nitro 服务层负责权限、导入、AI 编排、审核、发布和公开查询。
- 浏览器、公开前台或 AI worker 不能获得通用 Directus 写权限来绕过状态、可见性、资料范围或角色检查。
- 每次 AI 运行至少记录：产品 Draft、来源快照、Schema/提示词/模型版本、操作者、耗时、错误、建议版本与人工处理结果。
- 一期应记录每次模型调用的成本归属与单次上限；具体模型和预算在接入真实 API 前另行确认。

## 10. 询盘与项目资料的保护

### D-19：询盘不自动进入产品 AI 资料包

- Inquiry / Technical Matching 与 Product 分表并关联；可记录产品候选、产品 Revision 快照、页面语言和来源渠道。
- Technical Matching 可只关联产品类别或应用，不强制关联具体型号。
- 客户 PII、客户附件、报价和项目沟通默认不能进入 Product Dossier、公共知识库或训练集；需要独立、明确的人为授权。

## 11. 一期实施顺序与验收门槛

### 实施顺序

```text
1. Product Schema + Media UUID 引用 + 资料可见性
2. Draft / Review / Published Revision 与公开 API 门禁
3. Import Batch / staging / 多 Sheet 校验 / 创建 Draft
4. 单型号资料范围、来源切片与 source snapshot
5. AI Suggestion + Evidence + 字段锁定（先可用模拟结果验证流程）
6. 人工审核、审计、页面预览与发布边界
7. 仅在明确授权后接入真实模型与费用控制
```

### 最小真实验收

- 选择一个真实型号（计划可用 LT-180C，实际以资料确认结果为准）完成：资料包 → Draft → AI Candidate → 人工确认 → 英文详情页 Draft → Review。
- 任何测试资料必须标注 `TEST ONLY — NOT FOR PUBLICATION`，不得进入公开页面、sitemap 或搜索引擎。
- 验证 1440px 桌面端与 375px 手机端：资料范围、证据、审核、队列与发布门禁均无横向溢出且可操作。

## 12. 明确后置事项

以下不阻塞一期，不得以“顺手扩展”方式提前施工：

- 复杂系列继承、Variant 配置器、BOM、库存、价格/兼容性引擎；
- 任意 Excel 自由识别、多供应商导入 Profile、批量 AI 采纳；
- ES/PT 自动发布、翻译记忆；
- 自动生成 PPT、报价、邮件、视频、社媒内容；
- 客户门户、多租户 UI、外部协作审批、HubSpot 双向同步；
- 模型微调、客户资料训练、多模型路由和高级质量看板；
- COS 迁移、外部 DAM、复杂数字版权管理。

尽管一期只服务 LITUBO 内部，数据层应预留 `organization/workspace` 隔离能力；不实施客户自助注册或多租户 UI。

在任何实施前，Claude 必须：

1. 阅读仓库根目录 `CLAUDE.md`、`docs/project/CURRENT-STATE.md`、`docs/project/MASTER-ROADMAP.md`；
2. 检查 Git 状态、相关服务状态和实际 Directus schema；
3. 将本文件与现有项目档案核对。若有冲突，停止并报告，不自行猜测、迁移或覆盖；
4. 一次只实施一个已授权模块；不接入真实 API Key、不产生 API 费用、不 push、不部署、不发布真实产品；
5. 每个模块完成后提供变更文件、测试、1440px/375px 验证、Git 状态、本地 commit 与 `CURRENT-STATE.md` 更新。
